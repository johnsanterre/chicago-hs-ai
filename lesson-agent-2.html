Tools: the model asks, your code acts

A tool is a function you describe to the model. It replies with the tool's name and JSON arguments; your code runs the function and returns the result. That handshake is how every real agent works.

3 · Read & play

Describing hands to a planner

Lesson 1's scripted planner always asked for the right thing, because we wrote the script. A real model needs to be told what actions exist. That is a tool description: a name, what it does, and what arguments it takes — written in plain language, sent along with the question.

The handshake, in order. You send the question plus the tool descriptions. If the model wants an action, it replies with a structured request — the tool's name and its arguments as JSON, like {"tool": "search", "query": "riverside garden founding"}. Your dispatch code looks the name up in a dictionary of functions, runs the real function, and sends the result back as the next message. The model reads it and continues. Nothing here is magic: the model writes a request in a fixed format, and a five-line dictionary lookup does the rest.

What deserves a tool? Things the model cannot know: today's facts, your private files, live pages. And things it cannot do reliably: arithmetic is the classic — models predict text, and text-shaped arithmetic goes wrong quietly, so professionals give the model a calculator tool instead of trusting its multiplication. Things the model already does well from memory — defining a word, translating a sentence — need no tool at all.

The safety line, again. The model can request any tool it wants; only the functions you put in the dispatch table can ever run. An agent with search and fetch can search and fetch. It cannot delete files, send email, or spend money, because you gave it no such hands. Deciding what hands to give an agent is a real design decision, and you will make it deliberately in the capstone.
